# Canvas Mode Sidebar Split Brainstorm

> Stage 0 | 2026-06-05 | 下一步：design

## 想做什么、为什么

当前 App shell 的左侧栏默认只展示“会话”，Canvas 模式虽然已经加入独立工作台入口，但用户进入 Canvas 后，左侧仍混杂普通工作台会话语义，顶部工具栏还承担了“新建会话”这类列表级动作，导致“我现在在操作什么记录”不够清楚。

这次讨论的目标，是把普通工作台和 Canvas 工作台的左侧记录分流：进入普通工作台时只看到普通会话，进入 Canvas 时只看到 Canvas 项目，并把新建动作挪到对应左侧区域，避免继续把顶部导航做成混合操作台。

## 考虑过的方向

### 方向 A：按当前工作台模式切换左侧列表

- 描述 / 价值 / 代价：普通工作台左侧显示会话，Canvas 工作台左侧显示 Canvas 项目；顶部全局新建按钮下放到左侧区域，让“新建什么”跟当前列表保持一致。用户心智最直接，进入哪一部分就只看那一部分的记录。代价是需要调整 MainLayout 和现有 Canvas 项目切换入口。
- 结论：选定。这是这次讨论最终收敛的主方向。

### 方向 B：保留单一左侧栏，在同一处混合展示会话和 Canvas 项目

- 描述 / 价值 / 代价：继续使用同一份左侧列表，只在文案或分组上区分会话和 Canvas 项目。改动小，但用户仍要先理解两套记录的区别，再决定点哪一类。
- 结论：否决。和“进入哪部分就显示谁的记录”的目标相冲突。

### 方向 C：通过顶部项目菜单切 Canvas，左侧继续只显示会话

- 描述 / 价值 / 代价：不改侧栏信息架构，只增强 Canvas 顶部项目菜单。实现较轻，但用户仍会在 Canvas 模式里看到普通会话列表，记录模型没有真正分流。
- 结论：否决。实际体验已经验证这条路不够直觉。

## 已敲定的设计点

- 已确认：普通工作台左侧只显示普通会话，Canvas 工作台左侧只显示 Canvas 项目。
- 已确认：顶部的“新建会话”不再放在全局导航上，而是移到左侧对应列表区域，让新建动作跟当前列表同域。
- 已确认：Canvas 工作台里的项目切换应以“Canvas 项目”为用户感知对象，普通会话概念不在 Canvas 左侧栏中出现。
- 已确认：Canvas 项目不再复用“当前普通工作台会话”作为直接上下文来源；新建 Canvas 的语义就是新建一个独立项目。
- 已确认：每个 Canvas 项目在数据层拥有自己的专属会话，但这个会话对用户不可见。用户进入 Canvas 时面对的是项目，不是“某个普通会话的另一种视图”。
- 已确认：删除 Canvas 项目只删除项目本身；与项目绑定的内部专属会话按项目生命周期一起处理，不把“删不删会话”暴露成用户决策。

## 选定方向与遗留问题

选定方向是做“模式化左侧栏”：普通工作台展示会话，Canvas 工作台展示 Canvas 项目，并把新建入口移动到各自的左侧列表区域。这样用户进入哪个工作台，就只面对那一类记录，不再需要在同一个侧栏里理解两套对象。

明显不做的是继续混合展示两类记录，或只靠顶部项目菜单维持 Canvas 项目切换。design 阶段需要重点细化的是：Canvas 项目列表项展示哪些摘要、左侧“新建 Canvas”如何组织、隐藏专属会话如何在 store / service 层托管，以及它和现有 generation / reference / history 链路的边界该怎样约束。
